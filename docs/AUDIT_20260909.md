# Audit -- what this branch built, what survives a change of architecture

Written 2026-09-09, after five played races and a reading of SRB2 NetPlus.
Everything here is either read from source or measured; the two are labelled.

## 1. What we built is not rollback, and the name matters

**Rollback (GGPO)** has no authoritative server. Every peer simulates the same
world, inputs are exchanged, each peer rewinds when a remote input contradicts a
guess. Divergence is impossible when the simulation is deterministic.

**What this branch built** is client-side prediction with server reconciliation --
the Quake 3 / Overwatch / Rocket League shape. The server is authoritative, the
client runs ahead on guesses, and the server's truth pulls it back.

**Ring Racers is neither.** It is deterministic lockstep with a consistency check,
and that check is the thing our design collides with.

## 2. The collision, read line by line

Ours:

| where | what it does |
|---|---|
| `d_clisrv.c:6820` | `runto += K_RollbackPredictAhead()` -- **`gametic` itself is advanced past `neededtic`** |
| `d_clisrv.c:6983` | `consistancy[gametic % BACKUPTICS] = Consistancy()` -- computed for every tic run, **speculative ones included** |
| `d_clisrv.c:6501` | the client **sends** that value, labelled with the speculative `gametic` |
| `d_clisrv.c:5683` | the server compares and, on a mismatch, `PT_WILLRESENDGAMESTATE` -- **a full state resend** |

So the client announces the checksum of a world it *guessed*, and the server
treats the difference as corruption. A predicted world is different by
construction; that is what predicting means. **Measured: seven
`Game state reloaded` per two-minute race, unchanged by every fix of the evening.**

That also reframes the stutter a person reported. Replay cost is down to about
2.5 ms of a 28.6 ms tic, but a resync is a `Downloading $$$.sav` plus a
`Loading savegame length 16382`, mid-race, seven times. A discrete hitch, which is
what "des sauts nets" describes better than a missed frame budget does.

⚠ And a second defect on the same path: `consistancy[]` is written in the tic
loop, **not** inside `G_Ticker`, so a correction that replays tics leaves the
stored checksum belonging to the pre-correction world. Even confirmed tics can
send a stale value after a rollback.

## 3. What SRB2 NetPlus does instead

Read from `git.do.srb2.org/JohnFrostFox/netplus`, cloned locally under
`_RingRacersRollback/_study/netplus`.

**They keep two clocks.**

- `gametic` -- authoritative. Its loop is still `while (neededtic > gametic)`. **It
  never runs ahead.** So `consistancy[gametic]` is always computed on a confirmed
  world and what leaves for the server is always real. They do not fight the
  check; they never feed it a guess.
- `simtic` -- speculative, runs ahead, and is what the player sees and acts in.

**Before advancing the real timeline they undo the simulation**
(`d_clisrv.c:5665`): `if (simtic > gametic && gameStateBufferIsValid[...])
P_LoadGameState(&gameStateBuffer[gametic % MAXLOCALSAVESTATES])`. The confirmed
world is put back, the confirmed tics run normally, and the state at the confirmed
frontier is saved for next time.

Their snapshot module is `p_savenetrb.c` -- the same job as our `k_rollback.c`.

Three other things worth taking:

- `cv_siminaccuracy` -- re-simulate only every N live tics, to spread the CPU cost
  instead of paying it every tic. Their answer to the budget problem we measured.
- `localTicBuffer[(liveTic - i) % MAXSIMULATIONS] = localcmds`, with the comment
  "if realtics>=2, it copies input to several tics, means we lag". **They hit our
  frame-rate-against-tic-rate problem and buffer the input per live tic.**
- `cv_netsteadyplayers` with per-player `histx/histy/histz` -- position history to
  smooth remote players inside the simulated view. The anti-rubber-band machinery
  we never wrote.

⚠ **What NetPlus does not solve, and neither do we.** Its README: a client-only
mod on top of vanilla lockstep, "Deterministic Prediction-Rollback based only on
input from the server", and the server-side half is marked **"(Not yet
implemented)"**. Its own documentation still tells players to rejoin if a desync
repeats. So the wall we hit is where a shipped, played implementation also stops.
Reaching their level is realistic; expecting the desync to disappear is not.

## 4. Inventory: what survives the change

Our diff against `05cca02c9` is **5805 insertions**. Sorted by whether a two-clock
design would keep it.

### Keeps, entirely -- and it is the expensive part

| what | size | why it is architecture-independent |
|---|---|---|
| `k_rollback.c` snapshot ring | 4079 lines | save and restore a world. Any prediction scheme needs exactly this, whichever clock it drives. Measured: restore **8.6 ms** late in a race, snapshot **152-187 KiB**, a replayed tic **2-3 ms**. |
| `p_saveg.cpp` determinism fixes | +1120 lines | `MobjIsArchived` (pointers to unarchived objects), per-viewport renderflags, precipitation not rebuilt (**12 ms -> 6 ms**), `oldcmd` archived, `followerskin` sign, `onconveyor` read order. A save that does not round-trip breaks *any* rollback. **Three are upstream bugs and should be offered upstream.** |
| the instruments | in `k_rollback.c` | `K_NameMobjField` (125 fields by `offsetof`), `P_NamePlayerField`, `K_NameTiccmdDifferences`, `K_LocateSnapshotRecord`, the soak, the offset histogram, the per-pass counter. This is how any netcode change here gets debugged. |
| the two-instance harness | `playtest.sh`, the scenarios | plus `rollback_lag`, without which every counter on a loopback reads zero with nothing wrong anywhere. |
| "replay a tic through the live loop" | `G_MoveTiccmdsIntoPlayers`, replay via `G_Ticker` | four separate divergences turned out to be one cause: a replay that reconstructs a tic instead of running it. True in any design. |
| the mindelay fix | `d_clisrv.c` client branch | a client was asking the server to delay **its own** input, then failing to predict it. Measured: contradictions **292 -> 75**, replay cost **~10 ms -> ~2.5 ms** a tic. Any predicting client needs this. |

### Goes, or moves

| what | why |
|---|---|
| advancing `gametic` past `neededtic` (`d_clisrv.c:6820`) | this is the collision. In a two-clock design the speculation runs on its own clock and the authoritative one is untouched. |
| the `cv_netticbuffer` skip (`d_clisrv.c:6975`) | it exists only to let `gametic` run ahead. Unnecessary once it does not. |
| prediction depth as a tuning knob (`rollback_loop N`) | measured to be a palliative: the offset is a distribution whose centre moves with the setup, and no depth zeroes it. |
| the reconciliation rate limiter | `ROLLBACK_RECONCILE_EVERY`, gated on `g_localwrong`. **Has never deferred once, in any run.** It can only defer somebody else's misprediction and there has never been one. |
| repeat-last remote prediction | never exercised: the only other player was stationary, and remote prediction was wrong **0 times out of 1140**. Unproven rather than wrong. |

**So the part that is architecturally wrong is at most ~250 lines of
`d_clisrv.c`, and not even all of those.** The 5200 lines of snapshots,
determinism and instruments are the part that took the time, and they keep.

## 5. What is measured and stands whatever happens next

- Restore **6.8 ms** early, **8.6 ms** late in a race; `P_RelinkPointers` more than
  half of it. Snapshot 120 KiB at the start, 318 KiB three minutes in.
- A replayed tic **1.85 ms** early, **2.0-3.1 ms** late. A sixteen-tic rollback
  late in a race is about **54 ms** against a **28.6 ms** tic: it does not fit, and
  a depth cap is the only answer. That is phase 6's question, answered.
- Determinism: five maps or modes, **no player-state failures**, every surviving
  difference presentation (`MT_SHADOW`, interpolation, shadows).
- Twelve replays out of twelve byte-identical, bots idle and a person driving.
- **Responsiveness is solved.** "Ça répond tout de suite", holding across every
  race since `cv_netticbuffer` was found, at 171 ms of artificial delay.

## 6. What to do

1. **Two clocks.** Keep `gametic` on confirmed tics only; run the speculation on
   its own clock from a restored snapshot; restore the confirmed world before
   advancing the real one. This is NetPlus's shape and it is the only one that
   does not fight the consistency check.
2. **Never send a speculative checksum**, and refresh `consistancy[]` during a
   replay. Two small changes, worth doing even before the pivot, because they are
   testable on their own against the seven resyncs a race.
3. **Then re-measure.** Every cost figure above was taken with the authoritative
   clock running ahead. The budget question changes shape when the speculation is
   a separate, throwaway timeline.

Next reading, offered and not yet done: **Odamex** for the Doom lineage's answer
to client-side prediction. (d2k is abandoned.) The question to take to it is the
one neither we nor NetPlus have answered: **what do you do when client and server
genuinely diverge, other than resending the whole state?**

## 7. Odamex: the question does not arise, because the server streams state

Cloned and read: `_study/odamex`, `client/src/cl_pred.cpp` (393 lines) and
`common/p_snapshot.cpp`. Descended from CSDoom, the original client/server Doom.

**We took them one question: what do you do when client and server genuinely
diverge, other than resending the whole state? They never have to ask it.**

`grep -rin "consistanc|consistenc|resync|full state"` over their common and client
code returns **nothing** of the kind. The only `CL_ResyncWorldIndex` resynchronises
the *clock* they interpolate received snapshots against -- not the world. There is
no checksum, no synch-failure path, and no full-state resend anywhere, because
there is no determinism requirement to violate: **the server streams authoritative
state per entity**, continuously, and every predicted thing is overwritten by it
every update. Divergence cannot accumulate.

**`CL_PredictWorld`, every frame:**

1. `predicting = true` -- one flag that suppresses sound and side effects for the
   whole pass. (Ours is `K_RollbackReplaying`; same idea, arrived at independently.)
2. Move predicted sectors back to their **latest server snapshot**
   (`CL_ResetSectors`).
3. Move the local player back to **its latest server snapshot** (`snap.toPlayer(p)`).
4. Re-simulate forward from the server's confirmed `p.tic` to `gametic`, feeding
   `localcmds[predtic % MAXSAVETICS]`.
5. **Remote players are not simulated at all.** `CL_PredictRemotePlayers` only
   calls `P_BumpPlayerCounters`; they sit where the server put them.
6. On a misprediction, **do not snap**:
   `P_LerpPlayerPosition(prevsnap, correctedprevsnap, cl_prednudge)` eases the
   player from the wrong position to the right one, and
   `netgraph.setMisprediction(true)` shows it to the player.

### What that says about our cost

**Their rollback is partial and per-entity: one player and the moving sectors.**
Ours restores and replays **a whole world -- around two thousand objects -- for a
correction that concerns one kart.** That is where 2 to 3 ms a replayed tic comes
from, and it is not a constant of the problem, it is a consequence of snapshotting
everything. Rocket League said the same thing in different words -- the car and
the ball live in different timelines -- so this is the second independent vote for
predicting less rather than predicting better.

### Three for three on the input

`localcmds[MAXSAVETICS]`, indexed **per tic**. NetPlus buffers `localTicBuffer`
per live tic and comments on it. **We keep one sample per pass and spend it on
several tics.** Both implementations that shipped do the thing we measured
ourselves needing, and neither treats it as a subtlety.

### What transplants, and what does not

| | verdict |
|---|---|
| **smooth the correction** (`cl_prednudge` lerp) | **transplants directly.** No wire change, roughly fifteen lines. It is the answer to "des sauts nets" -- currently every correction moves the world instantly. Best effort-to-answer ratio available. |
| **predict less** -- restore and replay only what must be | transplants in principle, hard in a kart racer where karts collide. But two independent sources now say it, and it addresses the cost rather than palliating it. |
| **a misprediction indicator** on screen | transplants. They show the player when prediction failed; we have only logs. |
| **state streaming** | **does not transplant.** Ring Racers sends inputs; a state-streaming server is a different netcode, and gives up compatibility with stock servers entirely. That is a project, not a fix. |

⚠ So the three implementations sit on a line. **Odamex** streams state and cannot
desync. **NetPlus** stays lockstep, keeps the authoritative clock honest and
predicts on a second one, and still tells players to rejoin sometimes. **We** stay
lockstep and let the speculation drive the authoritative clock, which is the one
position on that line that fights its own architecture.
